## 第一部分：两设备都有数据，A 改密码后，B 会发生什么

### 1.1 场景推演（基于当前代码逐行验证）

```
T=0  设备 A 改密码 P1→P2
     A 本地：changePassword() 生成 enc2 = wrap(MK_P2, dataKey)，写入本地 meta
     A 立即 sync（change_passphrase.dart:355，R3 已修复）→ 远端 manifest 更新为 enc2
     dataKey 本身不变（O(1) 设计）

T=1  设备 B 重登。B 本地 meta 仍是 enc1 = wrap(MK_P1, dataKey)
```

**B 用新密码 P2 登录 → 在密码输入框就被锁死，根本走不到 vault。**

- `login.dart:267`（表单校验）和 `login.dart:380`（_login 二次校验）用的是
  `sha256(passphrase) == PreferencesStorage.passPhraseHash`。
- `passPhraseHash` 是**设备本地**的，A 改密码不会（也不可能）同步到 B——B 上存的仍是 P1 的 hash。
- 于是 B 输入正确的新密码 P2，本地 hash 比对直接失败，提示"密码错误"。
  用户明明输入了正确密码，却被系统告知密码错误，且**没有任何出口**（没有"从远端恢复"入口）。

**B 用旧密码 P1 登录 → 能进首页、能看笔记，但会静默回滚 A 的改密码。**

- 本地 hash 校验通过（P1 是 B 本地的"正确"密码）→ `unlockLocal` 成功（本地 meta 还是 enc1，MK_P1 能解开）→ dataKey 注入，首页正常。
- B 下次同步时，`sync_engine.dart:150-178`：
  - `checkMigrationNeeded(enc2)`：enc2 != enc1 → 用本地 MK_P1 解 enc2 → 失败 → `migrationResult.failed`；
  - 引擎的兜底分支：尝试用本地 dataKey 解密远端 manifest items —— **成功**（改密码不动 dataKey！）；
  - 于是引擎判定为"场景 b：本端改了密码还没推送"，继续正常同步；
  - `_buildLocalManifest()`（`sync_engine.dart:298`）用**本地 enc1** 构建 manifest header → PUT 覆盖远端 enc2。
- **结果：A 的新密码包裹被 B 的旧包裹顶掉。A 下次同步时同样走"场景 b"分支再顶回来。**
  enc1 / enc2 在两端之间来回翻转（flip-flop），两端每次 sync 都返回 success，无人察觉。
- 若 A 此时已卸载 App 或不再同步：远端停留在 enc1，A 的改密码**实质失效**——
  攻击者拿到远端数据 + A 的旧密码 P1 即可解开 dataKey。用户以为改了密码，实际没改成。

**B 也在本地改密码（并发改密码）→ 同样的翻转战争。**

- A 推 enc(MK_P2a)，B 推 enc(MK_P2b)，双方 dataKey 相同、都能解对方 manifest items，
  都走"场景 b"认为自己是合法推送方 → encryptedDataKey 永久翻转，直到一端停止同步。

### 1.2 附带崩溃面

- `login.dart:397-401`：`await _initVault(passphrase)` 失败后**无条件** `pushReplacementNamed('/home')`。
  `_initVault` 失败只弹个 SnackBar 就返回。dataKey 未注入 → 首页任何读取抛 `DataKeyNotSetException`。
  当前被本地 hash 门禁挡住走不到这里，但只要出现"hash 校验过、vault 解锁失败"的路径
  （如本地 meta 损坏、未来加了远端辅助解锁但远端也不可达），就是白屏崩溃。

### 1.3 根因（三件套，缺一不可）

| # | 根因 | 位置 |
|---|------|------|
| 1 | manifest header 没有"密钥纪元"字段（keyFingerprint / keyVersion），B 无法区分"我密码错了"还是"他端改了密码" | `sync_models.dart:178` |
| 2 | `unlockFromRemoteManifest` 是死代码，新密码重登没有远端辅助解锁入口 | `vault.dart:255`（全工程无调用） |
| 3 | 登录口令体系（sha256 本地 hash）与同步密钥体系（PBKDF2/vault）互不通信，本地 hash 门禁把"合法的新密码"挡在门外 | `login.dart:267/380` |

引擎 `sync_engine.dart:154-160` 的注释自己也承认"区分方法：用本地 dataKey 试解远端 manifest"——
但改密码不动 dataKey，这个方法在"本端改"和"他端改"两个方向上**得到完全相同的结果**，区分不了。
这不是实现 bug，是协议缺字段导致的原理性缺陷（与 194332 文档结论一致）。

### 1.4 修复方案（写方纪律 + 读方守卫，互补闭环）

**方案 A（读方守卫，核心）：给 manifest header 加密钥纪元**

1. `ManifestHeader` 增加：
   - `keyFingerprint`：= H(MK)（固定 salt 下只由密码决定、跨设备一致；放在明文 header，
     安全性不劣于现有的 encryptedDataKey——后者本身就是等价的离线密码验证 oracle）；
   - `keyVersion`：单调计数器，`createNew=1`，`changePassword` +1。
2. `Vault` unlock 时顺带计算并持有 fingerprint；`changePassword` 生成新 fingerprint 并递增 version。
3. `SyncEngine._syncOnce` 下载远端 header 后先比纪元：
   - 纪元相等 → 现状流程；
   - 远端 `keyVersion` 更高 → **他端改了密码**：本地 dataKey 不变，笔记照常读写，
     但**绝不把本地旧 encryptedDataKey 写回远端**。实现细节：`_buildLocalManifest` 在纪元不匹配分支
     必须改用 `remoteHeader.encryptedDataKey` 构建本地 manifest（而非当前默认的本地 `_encryptedDataKey`），
     否则"PUT 时保留远端包裹"无从谈起；同时置 `passwordEpochMismatch` 状态 → UI 提示"密码已在其他设备修改，请输入新密码"；
   - 本端 `keyVersion` 更高 → 本端改的，正常推送新包裹。
4. 激活 `unlockFromRemoteManifest` 作为"新密码重登"的兜底入口。完整流程必须包含 salt 来源：
   ```
   输入密码 → GET manifest header（明文）→ 读 kdf.salt → 按 salt 派生 MK
   → 算 H(MK) → 比对远端 fingerprint → 匹配则用 header.encryptedDataKey + MK 解 dataKey
   → 注入 database + 更新本地 meta（encryptedDataKey / passPhraseHash）
   ```
   注意：salt 必须从 header 读取，不能依赖本地常量——这是 per-vault salt（见 P2-9）能落地的前提。
   当前固定 salt 实现下，本地常量与 header 值一致；切 per-vault salt 后，新设备唯一 salt 来源就是 header。

**方案 B（写方纪律，已大部分落地）**：改密码前 clean 门禁 + 改后立即 sync。
当前 `change_passphrase.dart` 已实现：强制备份、ping 服务器、改前强制 sync、未同步笔记警告、
改后立即 sync（`change_passphrase.dart:376-428, 355`）。**R3 已修复，确认。**
但注意：方案 B 单独不够——B 用旧密码登录后的"场景 b"误推照样回滚（见 1.1），方案 A 的守卫必须做。

**登录门禁改造（方案 A 的必要配套）**：
`login.dart` 的 sha256 本地 hash 校验失败时，不要直接宣判"密码错误"：

```
本地 hash 校验失败
  ├─ 尝试 Vault.unlockLocal（PBKDF2+GCM 是真正的密码验证器）
  │    ├─ 成功 → 说明本地 hash 过期（他端改过密码）→ 更新 passPhraseHash → 放行
  │    └─ 失败 → 若已配置同步后端 → GET manifest 仅解析 header
  │              ├─ fingerprint 匹配输入密码 → unlockFromRemoteManifest → 更新本地 hash + meta → 放行
  │              └─ 不匹配/后端不可达 → 才报"密码错误"
```

这套流程同时解决"B 新密码被锁死"和 R12 死代码问题。

**关于 SafeServer 的加分项（非必需）**：服务端可以加一条规则"拒绝 keyVersion 低于当前值的 manifest 写入"，
给 WebDAV 之外的部署提供兜底。但协议修复本身后端无关，WebDAV 同样受益。

## 第二部分：WebDAV 到底让客户端牺牲了什么

直接回答：**核心功能没有"无解"的；WebDAV 真正的代价是——所有正确性保证都必须由客户端协议自己完成，
没有任何服务端兜底。凡是客户端协议偷懒的地方，在 WebDAV 下都会被放大成不可逆事故。**

### 2.1 三后端能力对照（基于代码实际实现）

| 能力 | LocalFS | WebDAV | SafeServer |
|------|---------|--------|-----------|
| ETag 乐观锁 | ✅ 内容 hash 强 ETag，必然一致 | ⚠️ **可选**：服务器不返回 ETag 时退化为内容 hash，且 `If-Match` 可能被服务器**静默忽略**（`webdav_backend.dart:155-161` 自己注释承认）→ 乐观锁静默退化为 last-write-wins，引擎的 3 次重试救不回来 | ✅ 服务端锁内读-校验-写（TOCTOU 已修） |
| 服务端逻辑兜底 | ❌ | ❌ 不可能（哑文件存储） | ✅ 可加（keyVersion 防降级、速率限制等） |
| DELETE 删除 | ✅ 可用 | ✅ **可用**（DELETE 是 WebDAV 标准方法，坚果云/Nextcloud 都支持） | ❌ 当前 API 未提供 |
| 原子写 | ❌ 当前直接覆盖写（R13） | ⚠️ 依赖服务器实现 | ✅ tmp+rename |
| 枚举/查询 | 目录列表 | PROPFIND（未使用） | ❌ |

### 2.2 WebDAV 带来的三个真实架构约束

**1) 单 blob 全量 manifest——改一条笔记 = 重写整个索引。**

因为哑后端没有"按 note 存取元数据"的端点，所有笔记元数据塞在一个 manifest 文件里：
- 每次同步（哪怕只改一条）都要 O(N) 序列化 + 加密 + 整体上传；笔记多了以后每次同步都是全量 IO；
- **损坏无自愈**：manifest 一旦半写/损坏（WebDAV 服务器崩在 PUT 中途是有可能的），
  `sync_engine.dart:147` 的 `deserializeHeaderOnly` 直接抛 FormatException → `SyncResult.failure`，
  且**在成功解析之前永远走不到 PUT** → 所有设备同步卡死，唯一出路是手工去服务器删文件。
  建议：增加"manifest 无法解析 → 备份损坏文件（或重命名）→ 用本地数据重建 manifest 上传"的自愈路径；
  上传侧用"先传 manifest.json.tmp 再 MOVE 覆盖"（WebDAV MOVE 是标准方法）实现原子替换。

**2) ETag 不可靠 → 并发窗口比 SafeServer 大得多。**

两台设备并发同步时，SafeServer 靠服务端锁 + 强 ETag 必然有一方 412 重试收敛；
WebDAV 在不返回/不校验 ETag 的服务器上，两个 PUT 都 200，后者覆盖前者——
丢的是整份 manifest 里的元数据增量（blob 本身内容寻址不丢，但 manifest 里丢条目 = 远端笔记"消失"）。
这部分只能靠客户端自己做得更好来补偿：
- 短期间隔的 autoSync debounce（已有 3 秒）；
- 冲突时合并而非整覆盖（当前引擎已是"重新 GET → 重新合并 → 重试"模式，ETag 有效时是对的）；
- 文档里明确声明"WebDAV 服务器必须支持 ETag/If-Match"，并在 ping/init 时**主动探测**：
  PUT 一个临时文件读回 ETag，没有 ETag 就警告用户"该服务器不支持乐观锁，多设备并发可能丢数据"。

**3) 改密码这类"需要服务端仲裁"的语义，必须 100% 客户端协议化。**

这就是第一部分的问题。再次强调结论：**检测他端改密码不需要服务器**——fingerprint/keyVersion
放 manifest 明文 header 即可，WebDAV 照样能存能读能比。WebDAV 不是 H1 无解的原因，
只是没有服务端兜底把"客户端协议错误"放大成"不可逆回滚"。

### 2.3 一个被冤枉的点：GC 不是 WebDAV 做不到

R5（blob/墓碑永不清理、存储无限增长）的根因是 `SyncBackend` 接口没有 `deleteBlob`——
而不是 WebDAV 不能删。DELETE 是 WebDAV 标准方法。建议接口加：

```dart
Future<void> deleteBlob(String hash);           // 三个后端都能实现
Future<List<String>> listBlobs();               // LocalFS 列目录 / WebDAV PROPFIND / SafeServer 加端点
```

GC 策略：manifest PUT 成功后，list - manifest 引用的 hash = 孤儿 blob，删除；
墓碑按 updatedAt 超过 30 天且所有设备 manifest version 都越过它之后清理
（简化版：本端清理 + 随 manifest 传播）。

## 第三部分：其它代码 / 架构 / 同步 / 流程问题清单

按优先级排列。标注 [新] 的是本次新发现或在前序报告基础上补充的新细节；
标注 [已修复] 的是前序报告提出、现已确认修复的。

### P0 —— 阻断正确性

1. **改密码三件套**（详见第一部分）：keyFingerprint/keyVersion + 引擎纪元守卫 +
   登录门禁改造（激活 unlockFromRemoteManifest）。[前序已提，本次补充本地 hash 门禁这层根因]
2. **`_initVault` 失败仍导航首页**（`login.dart:397-401`）：vault 解锁失败只弹 SnackBar，
   然后照样进 home → dataKey 未注入 → `DataKeyNotSetException` 白屏。
   修法：失败时停留在登录页并显示错误，只有 success 才导航。[新]

### P1 —— 功能完整性（同步触发器整体缺失）

3. **新增/编辑笔记后不触发同步**（R2，未修复）：
   `editor_state.dart:53 addOrUpdateNote` 全工程只有 `deleted_notes.dart:109`（恢复笔记）调了 `autoSync()`。
   且触发不一致：恢复会同步，**永久删除（`deleted_notes.dart:118 hardDelete`）反而不同步**，
   软删除（移入回收站）也不同步。修法：在 `addOrUpdateNote` / `softDelete` / `hardDelete` /
   `restoreNote` 统一触发 `autoSync()`（共 ~4 处各 1 行）。
   重点：**softDelete 不同步危害等同于 addOrUpdateNote**——A 删到回收站、B 上笔记仍在正常列表，
   用户感知不一致且无任何提示，必须优先修。
4. **登录后不做初始同步**（`login.dart:_initVault → initBackend` 只初始化不同步）：
   B 设备登录后看不到 A 的笔记，除非用户自己摸到同步设置页手动点。
   修法：initBackend 成功后 `autoSync()`（或首页进入时触发一次）。[新]
5. **没有任何周期性/生命周期同步触发**：不在前台恢复时同步、不做定时同步。
   对一个"多设备同步"产品，同步实际上是完全手动的。建议至少加：
   App 回前台（`AppLifecycleEventHandler` 已有 resume 钩子位置）+ 登录后 + 编辑后（3）三处。[新]

### P2 —— 健壮性

6. **manifest 损坏无自愈**（见 2.2-1）：所有设备同步永久卡死的单点。[新]
7. **`checkMigrationNeeded` 把 `remoteVaultId` 填成了本地 vaultId**（`vault.dart:341`）：
   字段名与值不符；且 `migrateToRemote` 的 `copyWith` 不更新 vaultId、不写远端 vaultId 到 meta，
   导致 R4——vaultId 在两端之间来回翻转，"所有设备共享同一 vaultId"的设计不变量被破坏。
   修法：迁移时把远端 header 的 vaultId 一并落盘，`_buildLocalManifest` 用它。[前序 R4 + 新发现字段填错]
8. **blob 下载失败导致 manifest 条目抖动**（`sync_engine.dart:358-362`）：
   远端有、本地无的笔记，若本次 blob missing（他端刚 PUT manifest 还没传完 blob），
   该 uuid 不进 `mergedItems` → 本端 PUT 的新 manifest **把它从远端索引里删掉** →
   其他设备下次同步就看到这条笔记"消失"（要等源设备再次同步才复活）。
   修法：下载失败时把 `remoteItem` 原样保留进 merged（而不是丢弃），下次再补下载。
   副作用注意：保留 remoteItem 后本端 PUT 仍递增 manifest version，若某条 blob 持续下载失败，
   version 会无意义飙升。建议：下载失败的 uuid 在本次 PUT 中标记 `pendingBlob: true`，
   不计入 version 递增判定，或用单独重试计数（如连续 5 次失败后告警）。[新]
9. **固定 salt 的生态级彩虹表面**（`crypto.dart:60`）：全生态所有用户共用 `safenotes-v1`，
   相同密码 → 相同 MK。攻击者可以针对这个固定 salt 预计算一次彩虹表，通吃所有用户的
   encryptedDataKey 离线爆破。注释里"固定 salt 不影响安全性"在**单用户**视角成立、在**生态**视角不成立。
   修法：`kdf.salt` 字段本来就在 manifest header 明文里（新设备无需 MK 即可读），
   改为创建 vault 时生成随机 per-vault salt 写入 header，新设备按 header 里的 salt 派生——
   多端一致性不受影响，跨用户预计算直接失效。
   **项目约束**：CLAUDE.md 明确"开发阶段不需要任何兼容和迁移代码"，故直接切换到 per-vault salt，
   不做 fixed salt 兼容分支、不做存量迁移。创建 vault 时随机生成 salt 写入 header 即可。[新，重要]
10. **R6 时钟偏移**：LWW 用墙钟 `updatedAt`，时钟快的设备静默赢下所有冲突。
    折中方案：冲突时若两边 updatedAt 差值超过阈值（如 5 分钟）且 hash 不同，
    败方副本存入"冲突副本"区（或至少把败方内容写入本地一条新笔记）而不是直接覆盖丢弃。
11. **R5 blob/墓碑 GC**（见 2.3）。
12. **R13 LocalFS putManifest 原子写**（tmp+rename，与两个服务端实现对齐）。
    **优先级上调至 P1**：LocalFS 是开发/测试的默认后端，非原子写在测试中容易导致 flaky
    （测试中途崩溃留下半写 manifest），直接影响开发效率。修复成本极低（~5 行），应尽早做。

### P3 —— 清理 / hardening

13. **R8 `synced` 字段实质死亡**：引擎靠 hash 比对做决策，`markAllSynced()` 把全部笔记标 1
    包括本次上传失败的。要么引擎真正消费它（增量同步优化），要么删掉字段和索引。
14. **R11 登录口令 sha256 无盐无 KDF**：与同步层 PBKDF2-200k 形成反差。
    按第一部分的登录门禁改造后，sha256 hash 只作"快速通道"、vault 才是真验证器，问题自然消解。
15. **R9 `reEncryptAllNotes` 临时切换全局 `_dataKey`**：迁移期间并发 UI 读可能拿到错误的 key。
    迁移本身在事务里，建议迁移期间加 UI 遮罩或读锁。
16. **R10 远端下载笔记丢 createdTime**（`sync_engine.dart:564` 用下载时刻）。

## 附：关键结论一句话版

1. **改密码问题**：B 用新密码被本地 sha256 门禁锁死（连 vault 都走不到）；B 用旧密码能登录但会把旧
   encryptedDataKey 写回远端、与 A 来回翻转。根因是协议缺密钥纪元字段 + 远端辅助解锁是死代码 +
   登录口令体系与 vault 体系互不通信。修法 = 纪元字段 + 引擎守卫 + 登录门禁改造，全部客户端侧、后端无关。
2. **WebDAV 问题**：没有让任何核心功能"无解"，但把"客户端协议必须自己正确"的代价放到最大——
   乐观锁可能静默失效、无服务端兜底、manifest 单文件全量重写且无自愈。GC 做不到是接口没加 DELETE，
   不是 WebDAV 不能删。
3. **最被低估的问题**：新增/编辑笔记后不触发同步 + 登录后无初始同步——对多设备产品来说，
   同步目前实质是全手动的，这个修复只要几行，收益最大。

## 第五部分：Manifest 字段扩展建议

> 原则：既然要加 `keyFingerprint` / `keyVersion`，一次性把"可能有用且不降低安全性"的字段都补齐，
> 避免后续多次协议迁移。所有新增字段均为明文元数据，安全性不劣于现有 `encryptedDataKey`（后者本身就是
> 离线密码验证 oracle）。项目约束（CLAUDE.md）：不做兼容分支，直接切换 schema。

### 5.1 ManifestHeader 新增字段

| 字段 | 类型 | 说明 | 安全性 |
|------|------|------|--------|
| `keyFingerprint` | String | H(MK)，密钥纪元标识，跨设备一致（固定/per-vault salt 下均成立） | 与 `encryptedDataKey` 等价（都能离线验证密码），不降低安全性 |
| `keyVersion` | int | 密钥版本号，`createNew=1`，`changePassword` +1 | 计数器，无敏感信息 |
| `schemaVersion` | int | 协议 schema 版本号，从 1 开始，未来字段迁移用 | 计数器，无敏感信息 |
| `createdAt` | int | vault 创建时间（Unix 毫秒），首次启用同步时设置，后续不变 | 时间戳，无敏感信息 |

> **注意**：`lastModifiedBy`（已存在）即用户提到的"manifest 级 updatedBy"，语义重复，无需再加。
> `updatedBy` 扩展放到 ManifestItem 级别更有价值（见 5.2）。

### 5.2 ManifestItem 新增字段

当前 ManifestItem 仅有 `hash` / `deleted` / `updatedAt`，信息不足导致多个问题（R10 丢 createdTime、
GC 无依据、冲突无诊断）。建议新增：

| 字段 | 类型 | 说明 | 解决问题 |
|------|------|------|----------|
| `updatedBy` | String | 最后修改此笔记的设备 ID | 冲突诊断、审计；用户明确要求 |
| `createdAt` | int | 笔记创建时间（Unix 毫秒） | R10：远端下载笔记丢 createdTime |
| `deletedAt` | int? | 软删除时间（null 表示未删除） | GC：墓碑按 deletedAt 过期清理，区别于 updatedAt |
| `contentSize` | int | 笔记内容大小（字节） | GC 优先级、统计；hash 已能侧信道，不增加风险 |

### 5.3 安全性分析

1. **明文元数据不降低安全性**：所有新增字段均为元数据，不涉及笔记内容。攻击者拿到 manifest 后，
   已能通过 `hash` 暴力验证笔记内容（已知明文算 hash 比对），新增字段不提供额外侧信道。
2. **`keyFingerprint` 与 `encryptedDataKey` 等价**：两者都能离线验证密码正确性。
   `encryptedDataKey` 本身就是"用 MK 加密的 dataKey"——攻击者可离线枚举密码尝试解密。
   `keyFingerprint = H(MK)` 提供的密码验证 oracle 不劣于现有。
3. **`updatedBy` / `lastModifiedBy` 暴露设备 ID**：设备 ID 格式为 `<platform>-<id>`，
   暴露平台类型和设备唯一标识。威胁模型：能读到 manifest 的攻击者已能拿到所有笔记 hash
   和删除状态，设备 ID 不构成额外敏感信息。
4. **`contentSize` 侧信道**：理论上可暴露笔记大小。但 `hash` 已是更强的内容侧信道
   （攻击者可对猜测内容算 hash 验证），`contentSize` 不增加风险。

### 5.4 keyFingerprint 篡改 DoS 说明

**威胁**：`keyFingerprint` 放明文 header，若攻击者能写远端（如拿到 WebDAV 凭据），
可篡改 fingerprint 造成用户永远登录不上（本地 fingerprint 与远端不匹配）。

**威胁模型评估**：能写远端的攻击者本身就能 DoS——直接删除/覆盖 manifest 即可让所有设备同步卡死。
篡改 fingerprint 不增加新的 DoS 面。

**缓解（可选，非必需）**：未来可将 header 字段纳入 dataKey 的 MAC 签名范围
（即 header 也加密或签名），但当前威胁模型下可接受。文档记录此点即可。
