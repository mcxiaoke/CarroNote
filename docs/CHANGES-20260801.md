## [2026-08-01 19:14:26] - 生产侧根因 P7：adoptRemoteEpoch 纪元递增未触发 blob 重传

### 根因确认（真实数据取证）
- 排查 Windows 端真实数据库 `safenotes_sync.db`（8 条 manifest=2 / blob=1 笔记的
  生产源头），并与 Android 数据集交叉验证，锁定生产侧缺口：
  - `keyring.adoptRemoteEpoch`（`lib/sync/keyring.dart:765-781`）采用远端纪元时
    **只 copyWith dataKeyEpoch 并 persist，从不调用 `markAllForBlobReupload()`**。
  - `_buildLocalManifest`（`sync_engine.dart:1058`）对所有本地笔记乐观声明
    `blobKeyEpoch = keyring.dataKeyEpoch`。
  - `_itemsEqual`（`sync_engine.dart:1318`）比较 blobKeyEpoch → 本地声明 2、远端
    声明 2、hash 相同 → 走 L1202 skip 分支 → 旧纪元 blob 永不被重传。
  - 场景链：Android 迁移 dataKey（纪元 1→2）重传自己的 16 条；Windows 的 8 条
    epoch-1 blob 由 Windows 在 epoch 1 上传，Windows 随后经 `adoptRemoteEpoch`
    采用纪元 2（dataKey 值未变，走改密码分支）→ 未标记重传 → 乐观声明 2、blob
    仍是 1 → `_itemsEqual` 判定相等 → skip → 服务器永久 manifest=2/blob=1。
- Windows DB 佐证：`sync_meta` 无 `blob_reupload_pending` 键、25 条笔记全部
  `synced=1` 且 `synced_hash==content_hash`（该端从未标记重传、自认已收敛）。

### P7 修复（`lib/sync/keyring.dart`）
- `adoptRemoteEpoch` 在 `remoteDataKeyEpoch > current.dataKeyEpoch`（纪元实际递增）
  时调用 `database.markAllForBlobReupload()`，把本地 blob 标记为待重传。
- 闭环：标记后 `_mergeAndTransfer` 的 pendingReupload 分支（L1190）强制用当前
  纪元重新加密上传，服务器 blob 与新纪元声明收敛；与 `migrateToRemote` 的
  keyChanged 处理一致。dataKey 值未变，无需 `reEncryptAllNotes`。
- 改密码场景（纪元不变）不触发标记，避免无谓全量重传。

### 测试
- `test/sync/keyring_test.dart` 新增 2 个 P7 回归：
  - 「纪元实际递增时标记全部 blob 重传」：storeNote 2 条 → adoptRemoteEpoch(epoch 2)
    → `getPendingReuploadUuids()` 含全部本地 uuid。
