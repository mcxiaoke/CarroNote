## [2026-08-01 19:14:26] - 生产侧根因 P7：adoptRemoteEpoch 纪元递增未触发 blob 重传

### 根因确认（真实数据取证）
- 排查 Windows 端真实数据库 `safenotes_sync.db`（8 条 manifest=2 / blob=1 笔记的
  生产源头），并与 Android 数据集交叉验证，锁定生产侧缺口：
  - `keyring.adoptRemoteEpoch`（`lib/sync/keyring.dart:765-781`）采用远端纪元时
    **只 copyWith dataKeyEpoch 并 persist，从不调用 `markAllForBlobReupload()`**。
  - `_buildLocalManifest`（`sync_engine.dart:1058`）对所有本地笔记乐观声明
    `blobKeyEpoch = keyring.dataKeyEpoch`。
  - `_itemsEqual`（`sync_engine.dart:1318`）比较 blobKeyEpoch → 本地声明 2、远端
    声明 2、hash 相同 → 走 L1202 skip 分支 → 旧纪元 blob 永不被重传。
  - 场景链：Android 迁移 dataKey（纪元 1→2）重传自己的 16 条；Windows 的 8 条
    epoch-1 blob 由 Windows 在 epoch 1 上传，Windows 随后经 `adoptRemoteEpoch`
    采用纪元 2（dataKey 值未变，走改密码分支）→ 未标记重传 → 乐观声明 2、blob
    仍是 1 → `_itemsEqual` 判定相等 → skip → 服务器永久 manifest=2/blob=1。
- Windows DB 佐证：`sync_meta` 无 `blob_reupload_pending` 键、25 条笔记全部
  `synced=1` 且 `synced_hash==content_hash`（该端从未标记重传、自认已收敛）。

### P7 修复（`lib/sync/keyring.dart`）
- `adoptRemoteEpoch` 在 `remoteDataKeyEpoch > current.dataKeyEpoch`（纪元实际递增）
  时调用 `database.markAllForBlobReupload()`，把本地 blob 标记为待重传。
- 闭环：标记后 `_mergeAndTransfer` 的 pendingReupload 分支（L1190）强制用当前
  纪元重新加密上传，服务器 blob 与新纪元声明收敛；与 `migrateToRemote` 的
  keyChanged 处理一致。dataKey 值未变，无需 `reEncryptAllNotes`。
- 改密码场景（纪元不变）不触发标记，避免无谓全量重传。

## [2026-08-01 09:08:27] - 冲突判定改为「共同祖先 base hash」，修复无限增殖与真并发静默丢数据

> 用户决策：**先修冲突判定 base hash（推荐）**，删除架构改造（独立 trash_notes 表 + 服务端真实删除）延后。
> 根因：原冲突判定用 `updatedAt` 时间差（>5 分钟判「真冲突」并保留副本）整个方向用反——衡量的是内容「新旧」而非「双方是否都偏离了上次同步的共同版本」，导致两向严重缺陷：
>   · **单边编辑误判为冲突** → 每台设备各把手里的旧版本另存成新 uuid 副本 → 长期测试实测**每代 +3 副本**无限增殖；
>   · **真并发误判为 LWW 覆盖** → 败方编辑被静默丢弃（实测 A 写的 v2 同步后凭空消失）。
> 正解：以本地 `syncedHash`（上次同步收敛时的 `content_hash`）为三方合并 base，区分「单边编辑」与「真并发冲突」。

### 新增 / 修改文件

- **`lib/models/safenote.dart`**：`SafeNote` 新增 `final String? syncedHash;` 字段；构造参数、`copyWith`、`fromJson`/`toJson`/`toString` 全部接入。该字段是 base-hash 判定的数据基础（本地收敛基线）。
- **`lib/data/database_handler.dart`**：
  - 生产 `_initDB` 升到 **DB version 3**，新增 `_upgradeDB`：v2→v3 `ALTER TABLE` 加 `synced_hash` 列，并对 `synced=1` 的历史笔记回填 `synced_hash = content_hash`（无基线的新笔记留 null，触发保守退化）。
  - 新增 `@visibleForTesting` 静态迁移钩子 `upgradeDBForTesting` / `_upgradeDBStatic`，供测试文件库对称挂载 `onUpgrade`，避免存量 v2 文件库 `no such column: synced_hash`。
- **`lib/sync/sync_engine.dart`**：
  - 冲突判定（约 1183–1200 行）改为 base-hash：`base = localNote?.syncedHash`；`localChanged = base==null || localItem.hash != base`，`remoteChanged` 同理；`shouldPreserveCopy = localChanged && remoteChanged && 双方活跃(非删) && hash 不同`。
  - **base==null 保守退化**：本地无同步基线（新笔记 / 迁移前未同步）时退化为「内容不同即保留副本」——绝不丢数据（顶多多留一份且仍要求双方活跃），也绝不复活删除。
  - 废弃常量 `kConflictPreserveThresholdMs` 已移除（仅保留注释说明旧逻辑为何错误）。

  - 用例 544（单边编辑）：改用 `readNoteByUuid` + `copyWith` 保留 `syncedHash`（原用 `SafeNote(...)` 新建会抹掉 base 触发退化），断言单边编辑**不增殖**（Expected 1）。
