# 2026-10-28 变更记录

## 2026-10-28 22:36:14 — fix(security): 生物识别凭据改为硬件绑定存储，移除解锁路径上的 local_auth 叠加

### 问题

原实现对「生物识别登录」只做了 UI 门控，硬件认证并未参与密钥保护：

- `BiometricAuth.setAuthKey()` 用随机 32B 包裹密钥加密 vault 密码，但**包裹密钥与密文
  写在同一个默认 `FlutterSecureStorage`（无任何 access control）**里——同时拿到两者即可
  还原明文，同机同用户进程可直接调用 `BiometricAuth.authKey` 解出密码，系统认证弹窗
  完全不参与；
- 登录页 `local_auth.authenticate()` 返回 true 之后才去读存储，属于「先拿 true 再读」，
  密钥的认证绑定没有被使用，硬件门控退化为 if 判断。
  （`docs/crypto-overview.md` 已知弱点 #2 已记录该问题。）

### 核对结论（避免误改）

- **PIN 路径不在此列**：`PinAuth` 用 `Argon2id(PIN#devicePepper)` 派生的密钥直接 seal
  vault 密码，未落盘任何可直接解封的中间密钥，属于密码学约束而非 UI 判断。
  其真实弱点是 `devicePepper` 取自 `deviceId` / `android.id`，并非保密值。
- `biometric_storage` 包（authpass）**没有 v11**，最新稳定版 5.0.1（2024-02-03），且
  Windows 走 wincred、Linux 走 libsecret，均无生物认证能力，无法解决本项目 Windows 桌面主场景。
- 「v11 + namespace」对应的实际是 `flutter_secure_storage` 11.x（v11 引入 `storageNamespace`）。
  已逐行核对原生实现后确认可用：
  - Android `ciphers/KeyCipherImplementationAES23.java`：`setUserAuthenticationRequired(true)`
    + `setUserAuthenticationParameters(0, authTypes)` + `setInvalidatedByBiometricEnrollment(true)`；
  - darwin `FlutterSecureStorage.swift`：`accessControlFlags` → `SecAccessControlCreateWithFlags`，
    `biometryCurrentSet` 映射 `.biometryCurrentSet`。

### 核心改动

1. **依赖升级**：`flutter_secure_storage ^10.3.1 → ^11.2.0`（10.0 已完成算法迁移，
   本次直接升 11 无数据风险）。
2. **`lib/models/biometric_auth.dart` 重写为双路径**：
   - **A. 硬件绑定（Android / iOS / macOS）**：独立实例 + 独立 `storageNamespace`
     (`biometric_credential`)，`AndroidOptions.biometric(enforceBiometrics: true)`、
     `IOSOptions/MacOsOptions(accessControlFlags: [biometryCurrentSet],
     accessibility: unlocked_this_device)`，macOS 额外 `usesDataProtectionKeychain: true`。
     凭据直接以明文密码写入（KEK 是系统密钥库里受认证保护的密钥，无需再包一层）。
     **读取即认证**：取消/失败直接抛异常，不返回任何明文。
   - **B. 桌面回退（Windows / Linux / Web）**：保留原 F-C01 包裹方案 + `local_auth`
     便捷门控，并在设置页明示「非硬件保护」。
   - 新增 `isHardwareBound` 能力标识与 `BiometricUnlockResult` /`BiometricUnlockStatus`
     （success / cancelled / notConfigured / failed），供 UI 区分「取消不计次」
     「凭据失效自动关闭开关」「真失败计次」。
   - `enable()` 改为**先写凭据再置开关**：写入在 A 路径会触发系统认证，用户取消时
     不会留下「开关开着但无凭据」的僵尸状态。
   - A 路径写入时主动删除旧版落在默认 store 的 `_secureBiometricAuthKey` /
     `_secureBiometricWrapKey`，避免升级后仍残留可解封副本。
   - `_deleteBound()` 在非硬件平台短路，防止 Windows 上 `deleteAll` 误清 WebDAV 密码等无关 key。
3. **`lib/views/authentication/login.dart`**：A 路径不再调用 `local_auth`，直接
   `BiometricAuth.unlock()`；桌面端抽出 `_desktopBiometricGate()` 并注明其只是便捷门控。
   `notConfigured` 时自动 `disable()` 并提示重新启用（换机 / 录入新生物特征使条目作废）。
4. **`lib/views/settings/biometric_setting.dart`**：启用流程去掉 A 路径的 `local_auth`
   前置验证（由写入触发认证）；说明文案按平台区分安全等级。
5. **`android/app/build.gradle`**：`minSdkVersion 25 → 28`（`enforceBiometrics` 的硬性要求，
   低版本会抛 `BIOMETRIC_UNAVAILABLE`）。

### 已知边界

- Windows / Linux **仍无硬件生物门控**：`WindowsOptions` 只有 `useBackwardCompatibility`，
  系统只提供 DPAPI（绑当前用户，不绑指纹）。设置页已如实标注，不使用「硬件保护」措辞。
- 硬件绑定路径无法在 Windows 测试宿主上覆盖，只能靠真机验证；单测覆盖的是桌面回退路径与结果分类。
