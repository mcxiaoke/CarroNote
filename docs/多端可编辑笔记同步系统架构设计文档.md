多端可编辑笔记同步系统架构设计文档
后端：WebDAV | 目标：可靠、工业级、真正双向同步（含删除）

1. 设计目标与非目标
1.1 目标

多端离线优先：任意设备可离线编辑，联网后最终一致。
真正双向同步：新增、修改、删除均正确传播。
内容级冲突处理：同一笔记并发编辑时尽量自动合并，无法合并时保留双方版本。
删除可逆与可审计：删除使用 tombstone，支持恢复与垃圾回收。
时钟漂移免疫：不以绝对时间作为唯一判断依据。
幂等与可重试：网络中断、进程崩溃后可安全重跑。
可扩展：支持加密、附件、笔记本层级、标签等。

1.2 非目标

实时协同光标（那是 CRDT 实时层的事情，可后续叠加）。
服务端业务逻辑（WebDAV 只做存储与基础元数据）。
跨用户协作权限管理（单用户多设备场景优先）。

核心原则：

客户端本地是唯一真相源（Local-first）。
WebDAV 只是共享持久化层 + 变更发现媒介。
所有决策在客户端完成，服务端无业务逻辑。


3. 核心数据结构
3.1 笔记实体（Note）
interface Note {
  id: string;                    // UUID v4，全局唯一，永不改变
  title: string;
  content: string;               // Markdown 或富文本序列化
  notebook_id?: string;          // 可选层级
  tags: string[];
  
  // 时间与版本
  created_time: number;          // 毫秒时间戳
  updated_time: number;          // 内容最后修改时间
  deleted_time?: number;         // 删除时间（tombstone）
  
  // 同步元数据
  rev: string;                   // 内容哈希 或 单调递增版本号（推荐 SHA-256 前 16 位）
  device_id: string;             // 产生本次变更的设备
  parent_rev?: string;           // 可选，用于简单 3-way merge
  
  // 加密相关（可选）
  encrypted?: boolean;
  encryption_applied?: boolean;
}

删除语义：deleted_time 有值即视为已删除（tombstone）。物理删除只在垃圾回收阶段发生。

3.2 同步记录（SyncRecord）—— 客户端本地 SQLite 核心表

CREATE TABLE sync_record (
  id              TEXT PRIMARY KEY,          -- 对应 Note.id
  path            TEXT NOT NULL,             -- WebDAV 上的相对路径，如 notes/{id}.md
  local_rev       TEXT,                      -- 本地内容哈希
  local_mtime     INTEGER,                   -- 本地 updated_time
  local_deleted   INTEGER DEFAULT 0,         -- 0/1
  remote_etag     TEXT,                      -- 上次同步时远端 ETag
  remote_mtime    INTEGER,                   -- 上次同步时远端 Last-Modified
  remote_deleted  INTEGER DEFAULT 0,
  last_sync_time  INTEGER,                   -- 上次成功同步时间
  conflict_state  TEXT DEFAULT 'none',       -- none / unresolved / resolved
  UNIQUE(path)
);

CREATE INDEX idx_sync_local_dirty ON sync_record(local_rev, local_deleted);

错误转移：

任何阶段网络错误 / 5xx → 指数退避重试 → 最终回到 IDLE。
冲突检测 → 进入 RESOLVING 子状态（自动或人工）。


4.2 单笔记决策状态（三方比较核心）
对每个 note_id / path，比较三个视图：

L：本地当前状态（存在 / 已删 / 内容 rev）
R：远端当前状态（通过 PROPFIND 或 sync-collection 获得）
S：上次同步记录（sync_record）

决策表（简化版，完整版约 20+ 种组合）：
L 存在,L 脏,R 存在,R 变,S 存在,动作
✓,✗,✓,✗,✓,SKIP
✓,✓,✓,✗,✓,UPLOAD
✓,✗,✓,✓,✓,DOWNLOAD
✓,✓,✓,✓,✓,CONFLICT
✓,-,✗,-,✓,DELETE_REMOTE 或 UPLOAD_TOMBSTONE
✗,-,✓,-,✓,DELETE_LOCAL 或 DOWNLOAD（恢复）
✗,-,✗,-,✓,CLEAN_RECORD
✓,-,✗,-,✗,UPLOAD（新笔记）
✗,-,✓,-,✗,DOWNLOAD（新笔记）

“脏”定义：local_rev ≠ S.local_rev 或 local_deleted ≠ S.local_deleted。
“变”定义：remote_etag ≠ S.remote_etag 或 remote_mtime ≠ S.remote_mtime（优先 ETag）。

5. 完整同步流程
5.1 触发条件

应用启动后延迟 3–10 秒
本地笔记变更后 debounce 2–5 秒
定时（默认 5–15 分钟）
网络从离线恢复
用户手动触发

5.2 详细步骤
Phase 1: Preparing

加分布式锁（本地进程锁 + 可选 WebDAV lock，防止同一设备多实例）。
加载本地所有 dirty 笔记 + sync_record。
读取本地 sync_token（如果有）。

Phase 2: Fetching

优先尝试 REPORT + DAV:sync-collection（RFC 6578）。
不支持则 PROPFIND Depth:1 获取整个 notes/ 目录的 ETag、Last-Modified、Content-Length。
对变更的文件再 HEAD 或 GET 获取精确元数据。
构建远端视图 map：path → {etag, mtime, size, exists}。

Phase 3: Deciding

对每个可能涉及的 path 执行三方比较。
生成有序操作队列（先处理删除/tombstone，再上传，最后下载，避免临时冲突）。
对 CONFLICT 条目进入冲突解决策略。

Phase 4: Executing

每个操作带 If-Match / If-None-Match（乐观锁）。
上传：PUT 完整文件（小笔记）或分块。
下载：GET → 写入临时文件 → 原子 rename。
删除远端：DELETE 或 PUT tombstone 文件。
失败重试（最多 5 次，指数退避 + jitter）。

Phase 5: Finalizing

成功操作更新 sync_record。
更新全局 sync_token / last_sync_time。
触发垃圾回收（过期 tombstone）。
释放锁，通知 UI。

6. 冲突解决策略
优先级从高到低：

CRDT 自动合并（推荐工业级方案）
笔记正文使用 Yjs / Automerge / Loro。
同步时交换 update binary，自动收敛。
适合真正的并发编辑。

3-way merge（基于 parent_rev）
如果双方都基于同一 parent_rev，尝试文本 merge。
成功则生成新 rev 并上传。

LWW + 保留双方
updated_time 新的胜出。
旧版本写入 .conflicts/{id}_{timestamp}.md。
用户可手动合并后删除冲突文件。

人工选择
UI 弹出两边 diff，用户选一边或手动编辑。


删除 vs 修改冲突：删除优先（安全默认），或生成冲突文件让用户决定。

7. 删除与 Tombstone 完整机制

本地删除：
设置 deleted_time = now()，content 可清空或保留。
标记 local_deleted = 1。
加入操作队列 UPLOAD_TOMBSTONE。

上传 Tombstone：
方式 A（推荐）：PUT {id}.md.deleted，内容为最小元数据。
方式 B：DELETE 原文件，同时在 meta 中记录删除事件。

远端发现删除：
决策表判定后执行 DELETE_LOCAL 或标记本地 tombstone。

垃圾回收：
默认 30–90 天后真正删除 tombstone 文件与本地记录。
可配置“永不物理删除”。

恢复：
用户从回收站恢复 → 清除 deleted_time，重新上传正常文件。

8. 可靠性保证

保证项,实现方式
最终一致性,三方比较 + 幂等操作 + 重试直到成功
不丢数据,冲突永远保留双方版本；删除用 tombstone
不重复执行,操作带 expected_rev / If-Match；sync_record 原子更新
时钟漂移免疫,优先 ETag / 内容哈希；时间仅作辅助排序
网络分区,本地继续编辑；恢复后自动追赶
进程崩溃,操作队列持久化；启动时从队列恢复
部分写入,下载先写临时文件再原子 rename；上传用完整 PUT
并发设备,乐观锁 + 冲突检测；同一设备多实例用文件锁
服务器不支持高级特性,优雅降级到全量 PROPFIND + 客户端状态机

9. 性能与扩展建议

增量优先：能用 RFC 6578 就用，否则只对比 ETag 变化的文件。
批量：一次 PROPFIND 拿目录，再并行 HEAD/GET。
附件独立：大附件用内容寻址（hash 命名），与笔记解耦。
加密：客户端 AES-GCM，密钥由用户密码派生，WebDAV 只见密文。
监控：记录每次同步的操作数、冲突数、耗时、失败原因。

10. 实现路线图建议

MVP：三方状态机 + LWW + tombstone + 基础 WebDAV（PUT/GET/DELETE/PROPFIND）。
可靠版：操作队列持久化、完整冲突保留、垃圾回收、RFC 6578 支持。
工业版：接入 CRDT（Yjs）、E2EE、附件、差量传输、完善测试与可观测性。


补充说明

E2E 端到端加密会显著改变同步架构的约束。下面是在原有设计基础上，针对 E2EE 笔记 的完整适配与强化。

1. E2EE 核心约束
约束,影响
WebDAV 服务器永远看不到明文,内容、标题、标签、笔记本名等全部客户端加密后上传
密钥只存在于客户端,必须支持多设备密钥派生 / 共享，且支持密钥轮换
冲突检测与合并必须在密文或解密后进行,不能依赖服务器做内容级 merge
元数据泄露最小化,路径、文件大小、更新时间仍可能泄露信息，需权衡
搜索、预览受限,默认只能本地搜索；如需服务端搜索需额外设计（通常放弃）

参考实现：Joplin 的 E2EE 模式是目前最接近工业级、且直接支持 WebDAV 的成熟方案。

2. 调整后的数据模型
2.1 加密后的存储格式（推荐）
每个笔记在 WebDAV 上存储为单个加密文件（或 header + 加密 body）：
notes/
  {note_id}.jenc          # 或 .md.enc / .bin

文件内部结构（客户端序列化后加密）：
interface EncryptedNoteBlob {
  // ---- 可公开或轻量加密的头部（可选）----
  version: 1;
  id: string;                    // 明文 UUID（方便索引，泄露有限）
  // 以下全部经过加密
  ciphertext: Uint8Array;        // AES-GCM 加密后的完整 Note 对象
  nonce: Uint8Array;             // 12 bytes
  // 可选：额外认证数据
  aad?: string;                  // 例如 note_id + rev
}

明文 Note 对象（加密前）保持之前设计，额外增加：
interface Note {
  // ... 原有字段
  encryption_applied: true;
  master_key_id: string;         // 使用的哪把主密钥
  // 内容本身已经是明文，整体被加密
}

2.2 密钥体系（工业级推荐）

用户密码 / 口令
    ↓ (Argon2id / scrypt)
Master Key (MK)          ← 真正加密数据的密钥
    ↓
Data Key (DK)            ← 每把 MK 可派生或直接使用
    ↓
加密 Note / 附件


多设备流程：

第一台设备：用户设置密码 → 生成 MK → 用密码派生密钥加密 MK → 上传加密后的 master_key.json（或存在本地 + 同步）。
新设备：输入同一密码 → 解密 MK → 即可解密所有笔记。
密钥轮换：生成新 MK，用旧 MK 加密新 MK（或重新加密所有数据），旧密钥保留一段时间。

绝对不要把明文密码或 MK 上传到 WebDAV。

2.3 SyncRecord 的调整
SyncRecord 本身不加密（它是本地状态），但要额外记录：

ALTER TABLE sync_record ADD COLUMN content_hash TEXT;  -- 密文哈希（用于快速判断是否变化）
ALTER TABLE sync_record ADD COLUMN master_key_id TEXT;

判断“是否脏”时，优先比较密文哈希或 ETag，避免每次都解密。

3. 同步流程在 E2EE 下的变化
3.1 上传（本地 → WebDAV）
本地明文 Note
    ↓
序列化（JSON / MessagePack）
    ↓
AES-256-GCM 加密（使用当前 Master Key）
    ↓
生成 EncryptedNoteBlob
    ↓
计算密文 SHA-256 作为 rev / 内容指纹
    ↓
PUT 到 WebDAV（带 If-Match 乐观锁）
    ↓
更新 sync_record（记录密文哈希 + etag）

3.2 下载（WebDAV → 本地）
GET 密文
    ↓
验证完整性（GCM tag）
    ↓
用本地 Master Key 解密
    ↓
反序列化得到明文 Note
    ↓
与本地版本做冲突检测 / 合并
    ↓
写入本地数据库

3.3 删除（Tombstone）
两种安全做法：
推荐做法 A（简单可靠）：

本地标记 deleted_time
上传一个加密的 tombstone 文件（内容很少，只含 id + deleted_time + 签名）
或直接 DELETE 原文件，并在本地 + 可选的加密 meta 中记录删除事件

做法 B（更强隐私）：

删除后把原文件重写为随机数据再 DELETE（防止服务端恢复）
但 WebDAV 通常无法保证安全擦除，实际收益有限

Tombstone 本身也建议加密，防止服务端统计“用户删了多少笔记”。

4. 冲突解决在 E2EE 下的策略
因为服务器看不到内容，所有智能合并只能在客户端完成：

最高优先级：CRDT + E2EE
使用 Yjs / Automerge / Loro。
同步的是 加密后的 CRDT update（或先合并再加密完整文档）。
推荐模式：本地维护明文 CRDT → 同步时生成 update → 加密 update → 上传；对端解密 update → 应用到本地 CRDT。

次优：解密后 3-way merge 或 LWW
下载双方密文 → 解密 → 比较 updated_time 或做文本 merge → 重新加密上传胜出版本。
冲突文件也加密存储。

密钥相关冲突
如果两端使用了不同的 Master Key（密钥轮换窗口），需要先同步密钥，再处理数据。

5. 可靠性保证的额外要求（E2EE 专属）
保证,实现要点
密钥永不离开客户端,Master Key 只存在内存 / 安全存储（Keychain / Keystore），WebDAV 只有加密后的密钥文件
密文完整性,必须使用 AEAD（AES-GCM / ChaCha20-Poly1305），防止服务端或中间人篡改
前向安全（可选）,支持密钥轮换，旧密钥加密的数据逐步迁移
设备丢失,用户可修改密码 → 生成新 MK → 使旧设备上的缓存失效（需重新同步）
备份,加密后的整个 notes/ 目录可直接备份，恢复时只需密码
侧信道最小化,文件名尽量用 UUID；避免在路径中暴露标题；文件大小变化会泄露信息（可接受的权衡）
